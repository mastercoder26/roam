# Production audit — 2026-09-22

**Production audit: 68/100, risky for a public release.** The score reflects passing local checks and the unresolved credential rotation, data retention, and live deployment verification. This is an engineering review of the current checkout, not a certification of the deployed services.

## Scope and evidence

- Reviewed the Express route and account APIs, Postgres repositories, deployment configuration, iOS auth and drive sync, and the Next.js route-planning flow.
- Ran backend build and tests, web typecheck and production build, iOS standalone checks and simulator builds, npm dependency audits, and `git diff --check`.
- Read public `/health` responses on 2026-09-22: `roam-data-api-n2sw.onrender.com` reported `database: up`; the Cloud Run route service reported `database: unconfigured`, as expected for its stateless deployment. These checks do not prove authenticated requests or Render plan status.
- An independent reviewer checked the backend, web, and deployment changes; a separate reviewer checked iOS changes.

## Bugs fixed in this audit

| Area | Finding | Change |
| --- | --- | --- |
| Backend | A Google Routes response could stall indefinitely while its body was read. | Keep the timeout active through body parsing; add a stalled-body regression. |
| Backend | A failed profile write could leave `users.display_name` updated but `driver_profiles` unchanged. | Write both changes in one database transaction, with rollback coverage. |
| Backend operations | Render's health check returned HTTP 200 during a configured database outage. | Return HTTP 503 when the configured database is down; retain HTTP 200 for the stateless route service. |
| iOS | A late drive-history response could apply after sign-out or an account switch; duplicate remote IDs could crash the merge. | Invalidate stale sync work and deduplicate remote revisions before merging. |
| iOS | A late profile response could restore signed-in state after sign-out or overwrite another account's profile. | Guard async results by session generation and keep Clerk and backend IDs separate. |
| iOS | Offline drive deletions could be stranded when the app switched from a Clerk ID to a backend UUID, and older sync metadata used the backend key. | Use a stable Clerk account key and migrate older metadata with deletion tombstones taking precedence. |
| iOS release | A Release archive could be built without API hosts. | Fail the Release build when either required HTTPS host is missing. |
| Web | A new analysis could reuse the previously selected alternate route; route ordering copy was inaccurate. | Clear prior results on submit and describe the actual primary-first ordering. |
| Web accessibility | Route fields lacked accessible names; errors and the map lacked nonvisual context. | Associate labels, announce errors, and provide a route summary. |
| Dependencies | Backend and web npm audits reported known vulnerabilities. | Refresh lockfiles and backend overrides; both audits now report zero known vulnerabilities. |
| Deployment docs | Cloud Run instructions incorrectly said to omit `CLERK_SECRET_KEY`, which the route API requires. | Correct the runtime contract and startup warning. |

## Remaining risks and release actions

1. **Rotate the Clerk secret before a public release.** `TODO.md` records that the current test key was pasted into a chat transcript. No matching credential was found in tracked source, but the rotation and service configuration have not been verified.
2. **Confirm Render database retention and backups.** `render.yaml` still declares a free plan, and the recorded 2026-09-05 expiration date has passed. The data API was healthy during this audit; only the Render dashboard can establish the actual plan and deletion schedule.
3. **Make account deletion recoverable.** `handleDeleteAccount` deletes the Clerk identity before the local database user. If the database operation fails, personal data can remain without an account that can retry. This needs a durable reconciliation design.
4. **Verify database TLS certificates.** Remote Postgres connections currently set `rejectUnauthorized: false`. Check Render's certificate chain and configure verification with a trusted CA before tightening this setting.
5. **Verify the live deployment gate.** `cloudbuild.yaml` runs tests before deploying, while the documented Cloud Run console trigger may deploy without those tests. Inspect the active trigger and make the tested path authoritative.
6. **Run a credentialed device end-to-end check.** Sign in, record and sync a drive, reinstall, recover it, and delete it. Local tests and public health checks do not cover that complete path.

No production configuration, credentials, databases, or deployed services were changed by this audit.
